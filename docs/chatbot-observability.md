# Local chatbot observability (Phase 2)

The live runtime is `sf-web-api`, not the document ingestion/evaluation repository
`sf-chatbot`. Tracing is optional and disabled by default. No AWS infrastructure
or production settings are needed or changed.

## Setup and start

1. Start the existing Phoenix service using
   [its README](../../sf-chatbot-observability/README.md). Open
   <http://localhost:6006>, sign in, and create a Phoenix API key.
2. From `sf-web-api`, activate `.venv` and install the API dependencies:

   ```bash
   source .venv/bin/activate
   python -m pip install -r requirements.txt -r requirements-dev.txt
   ```

3. Keep the existing database, Cognito, and AWS/Bedrock configuration in private
   `.env`. Add these settings (preserve any existing Phoenix key):

   ```dotenv
   APP_ENVIRONMENT=development
   CHATBOT_OBSERVABILITY_ENABLED=true
   PHOENIX_COLLECTOR_ENDPOINT=http://localhost:6006
   PHOENIX_PROJECT_NAME=silverfund-local
   # Set PHOENIX_API_KEY privately to the key generated by Phoenix.
   ```

   `CHATBOT_OBSERVABILITY_ENABLED=true` and an explicit environment of
   `development`, `dev`, or `local` are required. `PHOENIX_API_KEY` is required
   when enabled. Project name is optional (default `silverfund-local`); the
   endpoint defaults to `http://localhost:6006`. The existing `.env` loader is
   preserved: it uses `override=True`, so file values override shell values.

4. Start from the API directory:

   ```bash
   uvicorn app.main:app --reload --host 127.0.0.1 --port 8000
   ```

The ASGI lifespan owns initialization and shutdown. There is no startup network
probe. Invalid tracing configuration leaves the API running without tracing.

## Generate and find a trace

The development chatbot endpoint is the existing Cognito-protected
`POST /chat/stream`; no authentication bypass or new debug endpoint is added.
Use the local web app while signed in, or use a valid user token:

```bash
read -rsp 'Cognito access token: ' COGNITO_TOKEN; echo
curl --no-buffer --silent --show-error \
  http://127.0.0.1:8000/chat/stream \
  -H "Authorization: Bearer $COGNITO_TOKEN" \
  -H 'Content-Type: application/json' \
  --data '{"message":"What does tracking error mean?"}'
unset COGNITO_TOKEN
```

Use only an API connected to development data for local testing. AWS credentials,
Bedrock model access, and a reachable database are still needed for a successful
answer. The model IDs, prompts, retrieval query, tool behavior, source formatting,
and SSE event payloads remain unchanged.

Copy `requestId` from the `meta` SSE event. In Phoenix, select project
**silverfund-local**, wait a few seconds, and open the `chatbot.request` trace.
Its metadata `request_id` and span attribute `silverfund.request_id` equal that
SSE ID. This is the stable answer correlation identifier for future feedback;
there is no feedback endpoint or rating implementation in this phase.

The trace contains:

| Span | Captured metadata |
| --- | --- |
| `chatbot.request` (CHAIN) | Request ID, wall duration, sanitized error type, cancellation |
| `chatbot.embedding` (EMBEDDING) | Embedding stage and model ID; priced child `chatbot.bedrock.embedding` records actual inference usage |
| `chatbot.retrieval` (RETRIEVER) | Returned source count, numeric citation IDs, duration |
| `chatbot.bedrock` (LLM), one per round | Model ID, token counts, duration, `silverfund.final_answer`, `silverfund.tools_enabled` |
| `chatbot.tool` (TOOL), one per requested read | Allowlisted name, duration, error type, `tool.cache_hit`, request-local `tool.call_group` |

All children share the root trace ID. Each pipeline span includes `silverfund.fund`
with the canonical selected fund or `all_funds`. Fund context is restored on every
iterator advance and does not leak between worker threads or requests. Rejected tools are error spans even when
the model recovers and the overall request succeeds. Citation IDs are local to
the answer; document names and evidence text are not exported. A Bedrock span
covers invocation and stream consumption through final usage metadata. The root
span covers generator execution through exhaustion or disconnect, including
pauses between SSE chunks. Context is attached only during each iterator advance
or close, so thread-pool scheduling and concurrent streams do not mix spans.
The streaming response closes the pipeline on send failure/cancellation.
An in-flight synchronous Bedrock read must return (bounded by its existing read
timeout) before cancellation can close that generator.

## Export and library boundaries

The integration uses the pinned OpenTelemetry API/SDK and OTLP HTTP exporter
`1.45.2`, with `openinference-semantic-conventions` `0.1.44`. Manual spans use
OpenInference kinds and LLM usage attributes recognized by Phoenix. No automatic
Bedrock, HTTP, SQL, or FastAPI payload instrumentation is enabled. The module
owns a provider rather than changing the global OpenTelemetry singleton.

The configured base URL is normalized to **`http://localhost:6006/v1/traces`**
for **OTLP HTTP/protobuf**, not gRPC. Explicit `/v1/traces` also works. Only
loopback HTTP(S) endpoints are accepted; other paths, URL credentials, query
parameters, and fragments are rejected. Export uses the configured key in
`Authorization: Bearer <key>`; dashboard cookies are not used.

A `BatchSpanProcessor` exports on its worker thread with a 512-span queue,
64-span batches, a one-second schedule, and a two-second exporter timeout.
The exporter timeout bounds HTTP/retry work; the processor timeout alone is
not relied upon to interrupt I/O. A full queue drops telemetry. There is no
flush or collector wait in the SSE generator. Shutdown drains the bounded
queue off the event loop. Outages may lose traces but cannot fail answers.

Official API references checked for this implementation:

- [Phoenix authentication and trace headers](https://arize.com/docs/phoenix/self-hosting/features/authentication)
- [Phoenix endpoint documentation](https://arize.com/docs/phoenix/learn/resources/faqs/what-is-my-phoenix-endpoint)
- [OpenTelemetry Python exporters](https://opentelemetry.io/docs/languages/python/exporters/)
- [OpenInference semantic conventions](https://github.com/Arize-ai/openinference/tree/main/python/openinference-semantic-conventions)

## Troubleshooting and privacy

- No project/traces: verify the explicit enable flag and development environment
  in `.env`, restart the API, finish a chat, and wait for the batch export.
  Requests rejected by Cognito do not enter the chatbot pipeline or create spans.
- Connection errors: verify `http://localhost:6006/healthz` and the existing Docker
  service. The API must run on the host for this loopback-only setup. A container's
  `localhost` refers to that container; remote/container collectors are outside
  the scope of this integration.
- `401`/`403` from export: use a Phoenix-generated API key, not a Cognito JWT,
  admin password, or dashboard cookie. Replace revoked keys privately and restart.
- `404`/protocol errors: HTTP ingest is `/v1/traces` on port 6006. Port 4317/gRPC
  is not used. Do not add `/v1/traces` twice.
- Safe startup warning: check the tracing settings without printing `.env` or
  the key. A malformed URL or missing key disables tracing; the API still starts.
- Missing usage: Bedrock must return a `metadata.usage` event. Partial/failed or
  cancelled streams may lack usage. Embeddings use `inputTextTokenCount` when
  supplied. No estimates are invented.
- Outages: inspect exporter warnings, restore Phoenix, and issue a new request.
  Failed exports are best effort, with no durable replay queue.
- Keep `.env` ignored. Never paste the Phoenix key or Cognito token into logs,
  commits, screenshots, URLs, or issues. Never enable SDK wire debug logging.
- By default, exported telemetry excludes user messages, answers, retrieved excerpts,
  document names, prompts, embeddings, tool arguments/results, Cognito claims/
  tokens, and AWS credentials. Errors contain class names only, without exception
  messages or stack traces. Optional root-span Q&A capture is described below; it
  requires explicit local-only opt-in and does not enable raw payload capture.
  Existing API logs and existing source SSE payloads are unchanged; protect them
  separately. Do not enable third-party auto-instrumentation alongside this setup
  without reviewing its payload capture policy.
- Phoenix persists metadata in its existing local volume. Follow that service's
  access/retention guidance. Disable tracing by setting the flag to `false` and
  restarting; already stored traces are retained.

## Tool budget and final answers

The existing `MAX_TOOL_ROUNDS=3` limits **tool-use rounds**, not individual calls.
A single response can request several tools. The API permits at most three
tool-enabled inference rounds followed by one final text-only inference when
needed; cache hits also consume their round, so repetition cannot extend the loop.
The final inference retains the same model, max output tokens, temperature and
SDK timeouts. It cannot execute tools or enter another inference loop.

Converse ToolChoice supports `auto`, `any`, and `tool`, not `none`. Finalization
therefore omits `toolConfig` entirely. Historical tool results are consolidated into user-role reference data with
human-readable query labels. The original question, source evidence and collected
results are retained; assistant tool-code messages and internal tool IDs are not
replayed as prose. This avoids encouraging the model to echo a protocol transcript.
The final request needs no tool declarations or typed tool-history blocks. Original system/fund instructions remain; an additional finalization
instruction asks for an answer from collected results and disclosure of gaps.
Tool declarations are absent at the API boundary; the restriction does not depend
on that instruction alone. An unexpected tool response, empty final answer,
invocation failure or stream failure becomes the existing safe SSE error, without
another model call. `sources` and authoritative `answerContexts` retain their
existing success contract.

A request-local cache reuses successful allowlisted read-only results for the same
tool and effective JSON arguments (key order independent, selected fund included).
Each reply keeps its new toolUseId. Different arguments, funds and requests do not
share cached results; failures/rejections are not cached. A known successful result
is a request snapshot, not a cross-request or persistent financial-data cache.

The final `chatbot.bedrock` span has `silverfund.final_answer=true` and
`silverfund.tools_enabled=false`; the root has `silverfund.tool_limit_reached=true`.
Final-call failures mark both final inference and root spans ERROR with sanitized
error type. Cache-hit tool spans remain visible with `tool.cache_hit=true` and the
same numeric `tool.call_group` as their originating successful read. Those group
numbers are meaningful only within a request; no tool inputs or argument hashes
are exported.

The original failed trace `d408c06e52c7a954b0aeb564c0ae61f7` records one
`get_top_positions` and two `get_dividends` spans. It contains no tool arguments,
so their equality cannot be determined retroactively. Repeated names alone do not
establish a duplicate (tickers/date ranges may differ).

References: [ConverseStream](https://docs.aws.amazon.com/bedrock/latest/APIReference/API_runtime_ConverseStream.html),
[ToolChoice](https://docs.aws.amazon.com/bedrock/latest/APIReference/API_runtime_ToolChoice.html),

## Readable flow, costs and answer safety — November 12, 2026

The website must never display internal tool JSON as an answer. A small streaming
text guard withholds a 64-character tail to catch protocol markers split across
chunks. Invalid protocol output becomes a controlled SSE error; it is never
substituted with invented financial figures. The bounded model stream is drained
without exposing invalid text so its final usage metadata can still be priced.
A stream/network failure before usage arrives remains explicitly unpriced.
Ordinary longer answers still stream before the inference completes.

For “last/latest dividend received”, the new read-only `get_latest_dividends`
tool searches positive recorded dividends across the selected fund's holdings
without a model-invented date range or ticker. An explicitly supplied ticker can
narrow the query. It returns records from the newest available date (up to 50,
with a truncation flag), or an explicit empty result. It uses the same canonical
fund validation, account mapping and selected-fund restrictions as the other
tools. This reads `holding_returns`; it does not create or update accounting data.

In Phoenix's `silverfund-local` project, open the latest `chatbot.request` trace:

```text
chatbot.request
  chatbot.embedding
    chatbot.bedrock.embedding     model tokens + estimated cost
  chatbot.retrieval               source count + citation IDs
  Round 1: model and tools
    chatbot.bedrock               inference tokens + estimated cost
    chatbot.tool                 tool.name, duration, cache hit/group
  Round 2: model and tools
    chatbot.bedrock               next inference
  ...
  Round 4: final answer           only when the three-round budget is exhausted
    chatbot.bedrock               tools disabled; result or sanitized error
```

Round spans cover inference and execution together. Their safe `silverfund.round`
and `silverfund.phase` attributes make ordering/filtering explicit. Leaf spans
retain the same request trace and selected-fund context. Parent/round spans do not
carry duplicate token costs. The tracing decorator preserves generator return
values as well as context across worker threads.

### Cost setup and interpretation

`app/telemetry_costs.py` calculates USD **list-price estimates** using reported
usage and the verified public AWS Oregon price snapshot (2026-11-11). Current
supported entries, in USD per million tokens:

| Model | Input | Output |
| --- | ---: | ---: |
| `us.amazon.nova-2-lite-v1:0` | 0.33 | 2.75 |
| `amazon.titan-embed-text-v2:0` | 0.02 | 0 |

Source: [AWS public Oregon catalog](https://pricing.us-east-1.amazonaws.com/offers/v1.0/aws/AmazonBedrock/20261111013037/us-west-2/index.json).
Rates are region/model specific. Global inference, other models/regions, future
cache-enabled configurations and missing usage are not silently assigned a zero
estimate. See `silverfund.cost.status`: `estimated`, `unknown_price`,
`cache_pricing_unavailable`, or `usage_unavailable`. No live pricing/billing query
runs in a chatbot request. Reverify the public rates before changing configurations.
These estimates exclude discounts, taxes, provisioned capacity, retries without
reported usage, RDS hosting and other infrastructure charges.

The running Phoenix version prices only LLM spans. Its built-in model catalog
had no matching entries for the configured Nova/Titan IDs, so two exact-match,
AWS-provider local entries were added. The actual embedding inference is nested
as an LLM child beneath the retained EMBEDDING stage so its Cost column and trace
rollup work. No parent duplicates that charge. Financial SQL tools show timing
and cache hits; they do not have a separate token charge or an invented database
per-call price.

To inspect/recreate these **local Phoenix settings** from `sf-web-api`:

```bash
.venv/bin/python -m scripts.configure_phoenix_costs
# Only if entries are missing, explicitly apply to loopback Phoenix:
.venv/bin/python -m scripts.configure_phoenix_costs --apply
```

The script reads the private Phoenix key, validates the loopback endpoint, creates
only missing entries, and stops if existing custom rates differ. It does not
access AWS billing, application databases, or production. No `.env` change is
needed. Cost configuration persists in the existing Phoenix volume.

To inspect costs, select the **Cost** column and open each embedding/model leaf
for prompt/completion tokens and `llm.cost.*` attributes. Phoenix calculates its
own cost column from the matching prices and rolls those costs up to trace/project
views. The application also exports `llm.provider=aws`, `llm.system=amazon`, region,
cost provenance/status, and `llm.finish_reason`. Content capture remains disabled
unless the local-only Q&A option below is explicitly enabled.
Old traces without provider/model/usage metadata may remain incomplete.

## Opt-in local question and answer visibility

Q&A capture defaults to **off**. To enable it, add the following to the private
**`sf-web-api/.env`** (not the Phoenix server's `.env`) and restart the API:

```dotenv
APP_ENVIRONMENT=development
CHATBOT_OBSERVABILITY_ENABLED=true
PHOENIX_COLLECTOR_ENDPOINT=http://localhost:6006
CHATBOT_TRACE_CONTENT_ENABLED=true
```

Keep the existing private `PHOENIX_API_KEY` and `PHOENIX_PROJECT_NAME=silverfund-local`.
No credentials should be pasted into commands, screenshots, commits or issues.
Only `local`, `dev`, and `development` environments qualify. Both enable flags
must explicitly equal `true` (case insensitive), and the active provider's
configured collector must match the current validated loopback endpoint. Remote
collectors, production/staging, disabled observability and missing providers all
refuse content capture. A remote URL is rejected even if an in-memory exporter
is injected for tests or a previously local provider is still active. The
flag cannot enable tracing or bypass endpoint validation by itself.

After sending a local question through the existing authenticated web app or
`POST /chat/stream`, open the root **`chatbot.request`** span in Phoenix. Its
Input/Output panels show these OpenInference attributes when capture completes:

| Attribute | Value |
| --- | --- |
| `input.value` | User question after credential redaction and length limits |
| `input.mime_type` | `text/plain` |
| `output.value` | Concatenated assistant SSE deltas, redacted and bounded |
| `output.mime_type` | `text/plain` |

The question is captured as actually passed to the chatbot service (after the
API's normal whitespace validation). The answer is taken from the same deltas
already being sent to the client, including streamed prose and citation markers.
No second generator pass, Bedrock invocation, retrieval or financial-tool call
is made. Child spans remain metadata-only. Request IDs, fund scope, costs, usage,
citations and SSE payloads are unchanged. Redaction modifies telemetry only;
the answer sent to the browser is unchanged.

Capture never reads or serializes `sources`/`answerContexts` frames, raw document
content, tool arguments/results, system prompts, authentication headers, or API
keys from the pipeline. **Questions and generated answers can themselves contain
private financial information or quote source material.** That user-visible text
is the content being opted into; this setting is not an anonymization feature.

Privacy limits and redaction:

- Input limit: **4,000 characters**. Output limit: **16,000 characters**.
  Raw accumulated answer storage is capped at **32,000 characters per request**
  and cleared on finalization. Redaction runs before exported-value truncation;
  known long credentials clipped at the buffer boundary are also removed.
- Known configured credential values (at least four characters long) are removed
  for secret-related environment names, including AWS credentials/session tokens,
  Phoenix/API keys, passwords and private keys. Pattern redaction also covers
  Bearer tokens, JWT-like tokens, AWS access-key IDs, `sk-` API keys, named
  credential assignments and PEM private-key blocks. Output redaction happens
  after combining deltas, so chunk boundaries do not defeat it.
- **Automatic redaction cannot guarantee removal of all sensitive information.**
  Names, balances, proprietary text, unusual credential formats and unrecognized
  secrets may remain. Use this only with local development conversations you are
  willing to persist in Phoenix. Never assume it makes production data safe.

`silverfund.content.status` identifies `completed`, `error`, `cancelled`,
`incomplete`, `empty` or `capture_error`. Only normal generator exhaustion **after
an SSE done event** publishes output. Partial/error/cancelled responses do not
publish `output.value`; their redacted question can remain on the trace. A close
immediately after yielding done is conservatively classified as cancelled until
normal exhaustion is confirmed. This records generation lifecycle rather than
guaranteeing client receipt of network bytes.

`silverfund.content.input_truncated`, `silverfund.content.output_truncated`, and
`silverfund.content.redacted` disclose bounded/redacted captures. An exception
from generator cleanup is recorded as a sanitized `stream.cleanup_error_type`
and ERROR status, and cannot prevent span finalization. Capture/parser failures
are best effort and never change chatbot response behavior. Export still uses
the same bounded asynchronous batch queue; collector failures do not interrupt
SSE and may lose a trace.

Set `CHATBOT_TRACE_CONTENT_ENABLED=false` and restart to restore metadata-only
telemetry. This does **not** delete content already stored in Phoenix's persistent
volume; use Phoenix's retention/deletion controls for existing traces. Keep the
collector authenticated and loopback-only. A synthetic verification question is
preferable to a real financial conversation when first testing this setting.
